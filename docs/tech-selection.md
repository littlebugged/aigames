# 技术选型

> 状态说明：本文档是选型的**唯一依据**。原型代码只是用来验证选型的可行性，不是最终形态。
> 未标注「已定」的条目都还需要拍板。

## 0. 先把约束摆清楚

这四条约束决定了后面所有的选择，所以放在最前面：

| 约束 | 含义 |
|---|---|
| 纯前端，无后端 | 没有服务器进程。动态能力只能靠 Serverless（Cloudflare Functions/KV/D1）或第三方 BaaS |
| Cloudflare Pages 托管 | 构建产物必须是静态文件。免费版给无限带宽，但有 20,000 文件/部署的硬上限 |
| 目标是人气 + 广告收入 | 内容量和获客渠道比技术栈重要。变现方式决定接入哪些 SDK |
| 一人、周末时间 | 每引入一个框架/服务，都要算上学习成本和维护成本 |

**关键推论**：约束 4 意味着技术栈要尽量"少而稳"。每多一层抽象（框架、ORM、状态管理），都是在消耗本该花在做游戏上的时间。

## 2. 逐项说明

### 2.1 游戏引擎：Phaser 4

**选定 Phaser 4（4.2.1，MIT）**

理由：

- 它是唯一**完整**的 2D 游戏框架——场景管理、Arcade/Matter 物理、输入、音频、资源加载、相机、粒子全内置。PixiJS 只是渲染器，物理、场景、输入都要自己写；自研一套的成本远超收益。
- 13 年历史、40,000+ star、550+ 贡献者，由 Phaser Studio 商业公司维护，不是个人项目。出问题时几乎任何报错都能搜到答案。
- MIT 协议，商用、上架门户、卖授权都没有授权成本。
- Phaser 4（2026 年 4 月稳定版）重写了 WebGL 渲染器，保留 v3 API，新增 `SpriteGPULayer`（单次 draw call 渲染百万精灵）。现在上车不会踩到下个大版本的迁移。

**要认下的代价**：

- 全量包 **1.38 MB（gzip 360 KB）**，这是当前原型实测的构建结果。Phaser 支持自定义构建裁剪用不到的模块，能把体积压到 300–500 KB 量级——列为后续优化项，不是当前瓶颈。
- 有自己的一套 API 习惯，需要适应。

**备选与排除**：

| 方案 | 结论 | 原因 |
|---|---|---|
| Kaplay | 备选 | 轻，几十行出原型。但前身 Kaboom 已于 2024-08 停更，社区分叉，长期维护存疑 |
| PixiJS 8 | 排除 | 渲染引擎不是游戏引擎，物理/场景/输入全要自己造 |
| Excalibur.js | 排除 | TS + ECS 架构不错，但生态和教程量远小于 Phaser，且仍在 1.0 之前 |
| Godot / Unity 网页导出 | 排除 | 空项目 9 MB+，Safari/iOS 兼容性有问题，加载体验差 |

### 2.2 构建工具：Vite 8 + TypeScript

**选定 Vite 8 + TypeScript**

理由：

- 构建产物就是纯静态文件，和 Cloudflare Pages 天然契合。
- 本地开发体验（HMR）好，改一行代码立刻看到效果——做游戏调手感时这很重要。
- TypeScript 对游戏开发的价值特别高：`this.player.body` 这类链式 API 靠类型提示能省大量查文档的时间。
- **不引入框架**：不需要 React/Vue。游戏画面归 Canvas，站点 UI 归原生 HTML/CSS。为一个卡片墙引入 React 是纯负担。

**为什么不用 Next.js**：Next.js 的价值在 SSR、ISR、API Routes——这三样在一个纯静态游戏站里一个都用不上。静态导出后它产出的东西和 Vite 一样，但多了一层框架、一套约定和更大的构建开销。

**为什么不用 Astro**：Astro 适合内容密度高的站（博客、文档）。游戏站的交互全在 Canvas 里，Astro 的 island 模型帮不上忙。**但如果将来站内攻略/文章成为流量主体，Astro 值得重新评估。**

### 2.3 站点架构：多页

**选定多页（MPA）：每款游戏一个独立 HTML 入口**

理由（这是本次选型里最容易被忽略、但影响最大的一条）：

- **SEO**：每款游戏能有自己的 `<title>`、`description`、`canonical` 和独立 URL，可以被单独收录。单页应用里所有游戏共用一个 URL，等于放弃长尾搜索流量——而我们没有后端，自然流量几乎是唯一免费的获客渠道。
- **加载隔离**：Phaser 那 1.38 MB 只在该游戏页面加载。原型实测首页 JS 只有 **0.36 KB**，一个游戏都没玩过的访客不用为引擎付出代价。
- **故障隔离**：一款游戏崩了，不影响其他游戏和首页。
- 代价：加一款游戏要动 `vite.config.ts` 一行 + 复制一个目录。可控。

### 2.4 托管平台：Cloudflare（**需要你拍板**）

**为什么倾向 Cloudflare**：

- 免费版**无限带宽 + 无限静态请求**。游戏站天然是"资源大、流量不值钱"，这一条在整个市场里没有第二个选择能打。
- 边缘节点 300+，海外访问快。
- `_headers` 文件可以直接配置缓存策略和响应头。

**必须知道的硬限制**：

| 项 | 免费额度 | 影响 |
|---|---|---|
| 静态请求 / 带宽 | 无限 | 最大优势 |
| 部署文件数 | 20,000 | 每款游戏几十个文件的话能放几百款；大量图片音频时要盯着这个数 |
| 单文件大小 | 25 MiB | 超了只能放 R2 |
| 构建次数 | 500 / 月 | 够用，并发只有 1 |
| Functions | 10 万请求/天，**CPU 10ms/请求** | 将来做排行榜会撞到，10ms 比想象中紧 |

**必须知道的硬伤——中国大陆**：

Cloudflare 没有大陆节点。`*.pages.dev` 从 2022 年起在国内就不稳定（间歇性解析失败、超时，移动宽带最明显）。绑自定义域名能绕开域名层的污染，改善明显但不彻底。而且 **Cloudflare 无法做 ICP 备案**。

- 如果主要用户在国内 → Cloudflare 不是合适的选择。应该用腾讯云 EdgeOne Pages、阿里云 ESA，或者 COS/OSS + CDN + 备案域名。
- 如果主要用户在海外，或只是作品展示 → Cloudflare 是最优解。

**Pages 还是 Workers Static Assets**：两者的静态资源限制完全一样。但 Cloudflare 的重心正在往 Workers Static Assets 移，且 Workers 多出 Durable Objects、Cron Triggers、更完整的可观测性——将来做实时对战会用到 Durable Objects。**新项目建议直接上 Workers Static Assets**，避免日后迁移。

### 2.5 存档与后端：分阶段

**阶段一（现在）：localStorage**

零成本、零依赖、零请求。适合"本地最高分"这种单机数据。

**阶段二（需要排行榜时）：Cloudflare KV / D1 + Pages Functions**

要注意的是 Functions **计入 Workers 免费额度**：10 万请求/天，CPU 10ms/请求，单次最多 50 个子请求。10 ms 是 CPU 时间不是墙钟时间，对简单的 KV 读写够用，但**别在里面做复杂计算或服务端渲染**。

**备选**：Supabase / Firebase。如果哪天需要跨端账号体系、好友关系、实时对战匹配，它们比自己在 KV 上搭要省事。但对当前阶段是过度设计。

### 2.6 广告与变现（**需要你拍板**）

这是整份文档里最需要冷静看的一条。

**页面广告（网站边上挂 AdSense）——不建议作为主收入**

2026 年游戏/娱乐类的 RPM 是全类目垫底：Tier-1 流量 $1–8，中文流量再低 60–80%，实际约 **¥1–8 / 千次浏览**。也就是说日均 5,000 PV 的站，一个月几十块钱。而且按这个流量目标，纯静态站几乎只能靠自然搜索获客。

**游戏内广告——同一批流量，单价高 5–10 倍**

真正值钱的是游戏**里面**的插屏和激励视频：

| 格式 | 美国 rewarded eCPM |
|---|---|
| Rewarded video | $15–28 |
| Interstitial | 约为 rewarded 的一半 |
| Banner | 垫底，多数门户 SDK 直接不带玩 |

接入渠道：

- **Google H5 Games Ads**：要申请，通过后走 Ad Placement API，提供 interstitial 和 rewarded。
- **CrazyGames SDK / Poki SDK**：上架它们的平台才能用，但平台自带海量流量。
- **Playgama Ad**：一次 SDK 调用聚合 11 家 demand。

**游戏授权——一次性大额**

非独家授权约 $300–800 / 平台，一款游戏可以卖多个平台；独家从 $5,000 起。适合做完就有现金，代价是放弃长期分成。

**建议的顺序**：先把游戏做出来上架门户拿流量和数据，自建站的广告放在后面。原因很简单——**自建站最难的不是挂广告，是没人来**。

### 2.7 游戏内容来源：自研

**选定自研**，理由见前文分析：

- 用模板批量收录第三方游戏的站，正好命中 Google 的 **scaled content abuse** 政策（2026 年 3 月核心更新将其列为首要打击目标，中招站点流量掉 50–80%），2026 年 3/6/8 月连续三次 spam update。
- 内容完全同质化，没有任何护城河，换个人一天能复制一个。

**合规的替代方案**：GameMonetize / GamePix / Poki 的分发联盟提供了官方 embed API，是"合法但同质化"的路线。可以作为冷启动填充，但不应作为核心内容。

### 2.8 交付链路：GitHub → Cloudflare Pages 自动构建

**链路**

```
本地开发  npm run dev
   │
   ├─ push feat/xxx  ──→ 预览部署（独立 URL）
   │                     真机测试、发给别人试玩
   │
   └─ merge 到 main  ──→ 生产部署（自动构建 dist/ → 全球边缘）
```

**Cloudflare Pages 项目配置**

| 项 | 值 |
|---|---|
| Production branch | `main` |
| Framework preset | None |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Node 版本 | 由仓库根目录的 `.nvmrc` 指定 |

几个必须照做的点：

- **提交 `package-lock.json`**。Pages 用 `npm ci` 装依赖，锁文件保证本地和 CI 装出完全一样的依赖树。
- **用 `.nvmrc` 锁 Node 版本**。Cloudflare 的构建镜像换过默认 Node 版本（2025 年从 18 换到 22），不锁的话哪天 CI 突然挂了都不知道为什么。
- **每个非生产分支和 PR 都会自动生成独立预览 URL**。这对做游戏特别有用：改完手感直接推一版，手机扫码就能试，不用先合 main。
- **不要额外写 GitHub Actions**。Pages 自带的 Git 集成已经覆盖"构建 + 部署"全流程，再加 Actions 只是多一份要维护的配置。

**分支策略**

| 分支 | 用途 | 部署到 |
|---|---|---|
| `main` | 稳定可用版本 | 生产 |
| `feat/*` `fix/*` | 正在做的游戏 / 改动 | 预览，做完合并 |

一个人做不需要复杂的分支模型。唯一要守住的规矩是：**`main` 永远是可玩的**。因为门户的流量随时可能进来，作品展示链接也可能随时被点开。

**回滚**

Cloudflare Dashboard → 项目 → Deployments → 选任意历史部署点 Rollback，即时生效，比重跑一次构建快得多。这也是为什么要"构建成功再合 main"而不是"合了再看"。

**缓存策略**

已写入 `public/_headers`：

| 路径 | 策略 | 原因 |
|---|---|---|
| `/assets/*` | `max-age=31536000, immutable` | Vite 产出的文件名带内容 hash，内容变则文件名变，可以永久缓存 |
| `/*` | 不设强缓存 | HTML 必须能及时更新，否则用户拿着旧页面去引用已被删除的 JS |

同时加了 `X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy`。

**免费额度的边界（会影响你的操作习惯）**

- **500 次构建/月**。一个人开发够用，但别把每个小改动都推 main——每次 push 都是一次构建。
- **构建并发为 1**，高峰时会排队。
- 单次构建 20 分钟超时。

**没有采用的方案**

| 方案 | 为什么不用 |
|---|---|
| GitHub Actions 构建 + 部署 | 和 Pages 自带构建重复建设，还得自己想办法把产物传过去 |
| 本地 `wrangler pages deploy` | 仅作应急手段保留（`npm run deploy`），不作主链路，避免"本地能构建、CI 构建失败"的偏差 |
| Vercel / Netlify | 带宽要计费。游戏站资源大，Cloudflare 的无限带宽在这个场景优势太大 |

## 3. 待拍板的分叉

### 分叉 A：目标市场是海外还是国内？

这一个问题同时决定三件事：

| | 海外为主 | 国内为主 |
|---|---|---|
| 托管 | Cloudflare（最优） | 换 EdgeOne / ESA / 国内 CDN |
| 广告联盟 | H5 Games Ads / Poki / CrazyGames | 国内广告联盟（多需资质） |
| 游戏语言 | 英文 | 中文 |
| 获客渠道 | 门户分发 + 短视频 | 短视频 + 微信生态 |

### 分叉 B：起步路径

- **A 先做游戏**（我的建议）：做 1–2 款小游戏 → 上架 CrazyGames/Poki 拿真实数据和流量 → 有数据了再建自建站做品牌沉淀。
- **B 先做站**：先把站搭起来，游戏慢慢加。风险是站搭好了没人来，而"没人来"这件事只有游戏足够好玩才能解决。

## 4. 原型验证结果（已完成）

搭了一个最小原型来验证上述选型的可行性，**目的只是验证，不是成品**：

| 验证项 | 结果 |
|---|---|
| Phaser 4.2.1 + Vite 8 + TS 构建 | 通过，类型检查零错误 |
| 多页构建产物 | 首页 JS 0.36 KB；游戏页 JS 1.38 MB（gzip 360 KB）——加载隔离成立 |
| 渲染 | WebGL/Canvas 正常，无控制台报错 |
| 游戏循环 | 跳跃、障碍生成、AABB 碰撞、计分、结束、重开全部跑通 |
| 存档 | localStorage 写入与读取正常 |
| 部署配置 | `_headers` 缓存策略、`404.html` 已就位 |

**一个刻意的技术决定**：原型里没有使用 Phaser 的物理引擎和 Tween，重力、跳跃、碰撞检测全部自己算。原因是这两块是 Phaser 大版本间最容易变动的 API，自己实现只用几十行，却能消除升级时的风险。
